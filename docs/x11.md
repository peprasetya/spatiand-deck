# X11 applications

**X11 is not supported.** It runs, and it will keep running, and it is not a
thing to build on.

The distinction matters because both halves are true. XWayland is started, X11
windows appear in the room, take input, play sound and can be moved and closed
like any other window — VLC, Kodi, Firefox and every Windows game under Proton
work this way today, and a great many programs have no Wayland support and never
will. But X11 windows carry assumptions a room cannot satisfy, and where the two
disagree, the room wins and the application loses.

## What is wrong, and why it stays wrong

**A menu is a window.** X11 has no notion of a popup belonging to a window: a
menu is an ordinary top-level window with a flag asking the window manager to
leave it alone. Spatiand draws these on the surface of whichever X11 window has
focus, at the position X gave them, which is what makes VLC's menus look like
menus rather than extra panes floating in the room. It is a guess. With two X11
applications open, a menu from the one you are not using appears on the one you
are. There is no fix for this inside X11's model — the information simply is not
there.

**Position is meaningless.** An X11 application asks to be at a screen
coordinate. There is no screen. Position requests are refused and size requests
granted, so an application that carefully places a dialog gets it in the middle
of the room like everything else.

**One X screen, as big as the biggest window.** The X root window starts at the
size of a Spatiand window, because that is what `wl_output` says, and grows in
steps to hold the largest X11 window open. An application that sizes itself from
the screen therefore gets something sensible — but an application that expects to
*arrange* itself across a large desktop has nowhere to do it.

It grows because the pointer lives on the screen and cannot leave it. A window
dragged bigger than the screen had a corner the pointer could not reach: OpenTTD
resized, drew its own cursor from where X said the pointer was, and that cursor
stopped at the old edge. Measured on the Deck — a 1804x1174 window on a screen
`xdpyinfo` called 1280x800, with the compositor sending a click at 1786,1162 and
the X server putting the cursor at its own boundary instead.

**Override-redirect everything.** Tooltips, drag icons, splash screens and
combo-box dropdowns all arrive by the same route as menus and are all subject to
the same guess.

## What was fixed, and is worth knowing about

**Video was see-through.** An X11 window of depth 24 becomes an XRGB buffer:
eight bits where alpha would be, with nothing meaningful in them. Blending
against those bits made VLC's video invisible while its sound played, with the
room showing through where the film should have been. Window surfaces are now
drawn ignoring the alpha channel when the buffer has none. If you see this again
in some other application, that is the shape of the bug.

**Windows were "Untitled".** X11 windows have no xdg toplevel to read a title
from, so they were all labelled the same. They now use `WM_NAME`, falling back
to the window class.

**The close button did nothing.** Same cause: closing, focusing and resizing a
window each asked only for an xdg toplevel, found none on an X11 window, and
quietly did nothing. VLC could only be closed from its own menu. All three now
speak to X11 windows too — `WM_DELETE_WINDOW` to close, the keyboard and X's
stacking order to focus, a configure to resize. If some other window action works on Wayland
windows and not on X11 ones, look for a `toplevel()` that has no X11 branch.

**Keys went nowhere.** Focus is two things for an X11 window and only one of
them was being done. The keyboard was pointed at the Wayland surface XWayland
draws the window into, which delivers the keys *to the X server*, where they
stopped: X hands a key to whichever of its own windows holds its input focus, and
nothing here had ever set that. `xdpyinfo` said `focus: PointerRoot` — "whatever
the cursor is over" — against a window that had been clicked, raised and
highlighted. Anything that hides or grabs the cursor, which is every full-screen
game, received nothing at all.

The seat is now given the X11 window itself rather than its surface, which is
what sets X's input focus, sends `WM_TAKE_FOCUS` to a client that asked to be
told, and puts `_NET_WM_STATE_FOCUSED` on the window. The last two matter beyond
typing: Wine reads them to decide whether its window is in the foreground, and a
game that believes it is in the background ignores the *gamepad* as well as the
keyboard.

**Nothing had focus until it was clicked.** A window arriving took focus in the
layout — the highlight, the pointer, the controller mapping — and the seat was
never told. Only a click told it. So an application launched from the launcher
and never clicked inside had no keyboard focus at all, which is not something you
notice until you try to type into a game. The seat's focus is now settled against
the layout every frame.

## The recommendation

Write Wayland. `QT_QPA_PLATFORM=wayland;xcb` and `GDK_BACKEND=wayland,x11` are
in every launched application's environment, so a toolkit that can speak Wayland
already does, and the X11 path is only reached by programs with no other option.

If you are writing something new for this — see [apps.md](apps.md) — there is no
reason to go near X11, and the stereo and environment protocols will never be
available on it.

## Turning it off

`SPATIAND_XWAYLAND=off` starts the session with no X server at all. X11
applications then do not run, which is a clearer failure than running badly, and
everything else is unaffected.
